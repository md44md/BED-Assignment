## Feature 5 - Serve Customer & Advance Queue (with third-party email notification)

**User Story:** *As a Stall Owner, I would like to mark the current customer in queue as served and advance the queue, so that I could keep the queue moving and notify the next customer.*

**Endpoints under test:** `GET /stallowners/queue`, `POST /stallowners/queue/advance` (stall owner only, JWT-protected)

**Behaviour:** the queue is a stall's active orders for the current day (`pending` / `preparing` / `ready`), ordered by queue number - the head is the *current* customer. Advancing marks the head order `completed` (in a transaction) and promotes the next order to current. When a next customer exists, the back-end calls the **Brevo transactional email API** (third-party, invoked from the back-end) to email them "you're next", records the send in the `Notification` table, and returns `notified` in the response. A failed email never fails the serve action (recorded as `status: 'failed'`, `notified: false`).

**Evidence:** Postman screenshots in [`screenshots/hayder-zikry/feature5-queue-management/`](./screenshots/hayder-zikry/feature5-queue-management/)

### Test cases - View Queue (`GET /stallowners/queue`)


| # | Request                            | Expected                              | What it proves                                                |
| --- | ------------------------------------ | --------------------------------------- | --------------------------------------------------------------- |
| 1 | View Queue - Success               | `200` + `current` + `queue` array     | Owner sees their stall's active queue, current customer first |
| 2 | View Queue - Empty                 | `200` + `current: null` + empty array | An empty queue returns an empty result, not an error          |
| 3 | View Queue - No Token              | `401` Unauthorized                    | Endpoint requires authentication                              |
| 4 | View Queue - Customer (Wrong Role) | `403` Forbidden                       | Authorization is stall-owner-only                             |

### Test cases - Advance Queue (`POST /stallowners/queue/advance`)


| #  | Request                          | Expected                                               | What it proves                                                                |
| ---- | ---------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 5  | Advance - Success (notify next)  | `200` + `servedOrder` + `nextOrder` + `notified: true` | Head order is served, next promoted, and next customer emailed via Brevo      |
| 6  | Advance - Serves Last Customer   | `200` + `nextOrder: null` + `notified: false`          | Serving the last customer empties the queue; no one left to notify            |
| 7  | Advance - Empty Queue            | `404` no customer to serve                             | Advancing an empty queue is rejected                                          |
| 8  | Advance - Email Fails Gracefully | `200` + `notified: false`                              | A third-party email failure is caught; the serve still succeeds (row`failed`) |
| 9  | Advance - No Token               | `401` Unauthorized                                     | Endpoint requires authentication                                              |
| 10 | Advance - Customer (Wrong Role)  | `403` Forbidden                                        | Authorization is stall-owner-only                                             |

Seeded stall owner credentials: `diana@email.com` / `Diana123!` (owns Stall 1) &nbsp;|&nbsp; Seeded customer (for cases 4 & 10): `alice@email.com` / `Alice123!`

> **Setup - creating a queue to test against:** Stall 1 starts with no *active* orders today (its seeded order is already `completed`). Build a queue first by either (a) logging in as a customer and checking out 2+ orders at Stall 1, or (b) inserting `Orders` rows for `stallID 1` with today's date and `status 'pending'`. Then log in as Diana to view/advance.

> **Case 5 (notify next):** to capture `notified: true` and a real email, `.env` must have the Brevo keys set **and** the *next* order must belong to a customer with a real inbox (register a customer with your own email and place their order second in line). Without Brevo keys, this case behaves like **Case 8**.

> **Case 8 (email fails gracefully):** temporarily blank/wrong `BREVO_API_KEY` in `.env`, restart, then advance - the response is still `200` with `notified: false`, and the `Notification` row is logged with `status = 'failed'`.

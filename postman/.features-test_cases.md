## Feature 5 - Serve Customer & Advance Queue (with third-party email notification)

**User Story:** *As a Stall Owner, I would like to mark the current customer in queue as served and advance the queue, so that I could keep the queue moving and notify the next customer.*

**Endpoints under test:** `GET /stallowners/queue`, `POST /stallowners/queue/advance` (stall owner only, JWT-protected)

**Behaviour:** the queue is a stall's active orders for the current day (`pending` / `preparing` / `ready`), ordered by queue number - the head is the *current* customer. Advancing marks the head order `completed` (in a transaction) and promotes the next order to current. When a next customer exists, the back-end calls the **Brevo transactional email API** (third-party, invoked from the back-end) to email them "you're next", records the send in the `Notification` table, and returns `notified` in the response. A failed email never fails the serve action (recorded as `status: 'failed'`, `notified: false`).

**Evidence:** Postman screenshots in [`screenshots/hayder-zikry/feature5-queue-management/`](./screenshots/hayder-zikry/feature5-queue-management/)

## Feature 6 - View & Follow Up on Stall Complaints (NEA Officer Oversight)

**User Story:** *As a NEA Officer, I would like to view complaints submitted about stalls, so that I could investigate and take appropriate follow-up action.*

**Endpoints under test:** `GET /officers/complaints`, `PUT /officers/complaints/:complaintID/status` (NEA officer only, JWT-protected)

**Behaviour:** unlike the stall-owner complaint view (which is scoped to one stall), the officer view returns complaints across **every** stall, newest first - each row carries the stall, its hawker centre and the customer who raised it. The list accepts three **optional** query filters (`status`, `stallID`, `category`) that can be combined to narrow an investigation; no query string means "show everything". Recording follow-up action moves a complaint through `open → underReview → resolved/closed`; there is **no ownership check** because an officer has authority over all stalls, and `resolvedAt` is stamped when the complaint is resolved/closed and cleared again if it is reopened.

**Evidence:** Postman screenshots in [`screenshots/hayder-zikry/feature6-officer-complaints/`](./screenshots/hayder-zikry/feature6-officer-complaints/)

## Feature 7 - Change Email Address

**User Story:** *As a User, I would like to change my email address, so that I could keep my account information up to date.*

**Endpoint under test:** `PUT /account/email` (any logged-in role, JWT-protected)

**Behaviour:** a shared account route (mirrors `PUT /account/picture`) that lets any signed-in user update the email they log in with. The request confirms the account's **current password** with bcrypt before changing anything, then rejects an **unchanged** email or one **already in use**. Because `Users.email` is `UNIQUE` across *every* role, the uniqueness check is deliberately **not** role-scoped - a customer cannot take an email already held by a stall owner. On success it updates `Users.email` and returns the new address. A wrong current password returns `401`, distinct from the register/login `401`s.

**Evidence:** Postman screenshots in [`screenshots/hayder-zikry/feature7-change-email/`](./screenshots/hayder-zikry/feature7-change-email/)

Set **Body -> raw -> JSON** for the body column.

> **Run the failure cases (2-6) first, then the success case (1) last** - case 1 actually changes Alice's login email, so running it earlier would shift the "current email" that cases 3 and 6 depend on.

## Feature 8 - Auto-Abandon Uncollected Orders

**User Story:** *As a Stall Owner, I would like the system to automatically mark an order as "Abandoned" if uncollected after 45 minutes, so that we can clear the active order board and manage food waste tracking.*

**Endpoint under test:** `POST /stallowners/queue/abandon` (stall owner only, JWT-protected)

**Behaviour:** the active order board is a stall's orders for the current day still in `pending` / `preparing` / `ready`. This sweep marks any such order placed **over 45 minutes ago** (measured from `createdAt`) as `'abandoned'`, so it drops off the board for food-waste tracking, and returns the orders it cleared. It is scoped to the logged-in owner's stall via `stallOwnerID` from the JWT (never a client-supplied stall id), the same pattern as the queue view/advance routes. `count: 0` (nothing old enough) is a normal `200`, not an error. The same sweep **also runs automatically** at the top of `GET /stallowners/queue`, so the board self-clears whenever the owner loads it.

**Evidence:** Postman screenshots in [`screenshots/hayder-zikry/feature8-abandon-orders/`](./screenshots/hayder-zikry/feature8-abandon-orders/)

### How to authenticate

`POST /stallowners/login` with `{ "email": "diana@email.com", "password": "Diana123!" }` (Diana owns Stall 1), copy the `token`, and set `Authorization: Bearer <token>`. For the wrong-role case, log in instead as a customer: `POST /customers/login` with `{ "email": "alice@email.com", "password": "Alice123!" }`. This route takes **no request body**.

### Setup - age an order so it is "stale"

Seeded orders are created with `createdAt = GETDATE()` (now), so nothing is old enough to abandon on a fresh DB. To stage case 1, push one order's `createdAt` back past the 45-minute threshold in SSMS (order 4 is Stall 1, `preparing`):

```sql
UPDATE Orders SET createdAt = DATEADD(MINUTE, -46, GETDATE()) WHERE orderID = 4;
```

| 2 | Abandon - None Old Enough        | `200` + `count: 0` + empty `abandoned` array        | With nothing past the threshold, the sweep is a no-op success, not a`404`       |
| 3 | Abandon - No Token               | `401` Unauthorized                                  | Endpoint requires authentication                                               |

**Evidence:** Postman screenshots in [`screenshots/seah-hao-bin/feature1-order-submission/`](./screenshots/seah-hao-bin/feature1-order-submission/)

### Test cases

| # | Request | Expected | What it proves |
| --- | --- | --- | --- |
| 1 | Submit Order - Success | `201` + orderID, queueNumber, totalAmount | A valid cart is converted into an order, its items and a payment record in one transaction |
| 2 | Submit Order - No Token | `401` Unauthorized | Endpoint requires authentication |
| 3 | Submit Order - Stall Owner Token (Wrong Role) | `403` Forbidden | Authorization is customer-only |
| 4 | Submit Order - Invalid Payment Method | `400` validation error | `paymentMethod` must be one of Cash, NETS, PayNow |
| 5 | Submit Order - Missing cartID | `400` validation error | Joi requires `cartID` |
| 6 | Submit Order - Cart Not Found | `404` Cart not found | Cart existence is checked before ordering |
| 7 | Submit Order - Cart Belongs to Another Customer | `403` Access denied | A customer cannot check out someone elses cart |
| 8 | View My Orders - Success | `200` + orders array | Returns the customers own orders only, scoped by `customerID` from the JWT |
| 9 | View My Orders - No Token | `401` Unauthorized | Endpoint requires authentication |

> **Case 7** uses `cartID 2`, which belongs to Bob. Log in as Alice and target that cart to trigger the ownership check.

| # | Request | Expected | What it proves |

**User Story:** *As a Customer, I would like to submit a star rating and written review for a stall and edit it later, so that I could share and update my experience.*

**Endpoints under test:** `POST /feedback`, `POST /feedback/edit`, `GET /feedback` (customer only, JWT-protected)

**Evidence:** Postman screenshots in [`screenshots/seah-hao-bin/feature3-submit-edit-review/`](./screenshots/seah-hao-bin/feature3-submit-edit-review/)

### Test cases

| # | Request | Expected | What it proves |
| --- | --- | --- | --- |
| 1 | Submit Review - Success | `201` + feedbackID | A rating and comment save against a completed, paid order |
| 2 | Submit Review - No Token | `401` Unauthorized | Endpoint requires authentication |
| 3 | Submit Review - Stall Owner Token (Wrong Role) | `403` Forbidden | Authorization is customer-only |
| 4 | Submit Review - Rating Above 5 | `400` validation error | Joi enforces the 1-5 rating range |
| 5 | Submit Review - Order Not Found | `404` Order not found | Order existence is checked first |
| 6 | Submit Review - Order Belongs to Another Customer | `403` Access denied | A customer cannot review using someone elses order |
| 7 | Submit Review - Order Not Completed/Paid | `400` validation error | Only completed and paid orders can be reviewed |

| 10 | Edit Review - Not the Owner | `403` Access denied | A customer cannot edit another customers review |

## Feature 6 - Profanity Filtering on Reviews

**User Story:** *As a Customer, I would like offensive language in reviews to be automatically censored, so that reviews stay respectful for everyone reading them.*

**Endpoints under test:** `POST /feedback` and `POST /feedback/edit` (filtering applied on both), verified through the public `GET /stalls/:stallID/feedback`.

**Third-party API:** [PurgoMalum](https://www.purgomalum.com/) - the comment is sent to the filter before it is stored.

**Evidence:** Postman screenshots in [`screenshots/seah-hao-bin/feature6-profanity-filter/`](./screenshots/seah-hao-bin/feature6-profanity-filter/)

### Test cases

| # | Request | Expected | What it proves |
| --- | --- | --- | --- |
| 1 | Submit Review With Profanity | `201` + feedbackID | The review is accepted; submission is never blocked by the filter |
| 2 | View Stall Reviews - Comment Is Censored | `200` + comment shows `this **** was damn awful` | The offensive word was replaced before storage, so other customers never see it |
| 3 | Edit Review To Clean Text | `200` updated | The same filter runs on edit, not just on submit |
| 4 | View Stall Reviews - Clean Text Unchanged | `200` + comment shows `Actually pretty good` | Clean text passes through untouched, so the filter does not corrupt normal reviews |

> If the PurgoMalum API is unreachable the service returns the original text and the review still saves, so a third-party outage can never block a customer from leaving feedback.

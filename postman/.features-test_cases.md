## Feature 5 - Serve Customer & Advance Queue (with third-party email notification)

**User Story:** *As a Stall Owner, I would like to mark the current customer in queue as served and advance the queue, so that I could keep the queue moving and notify the next customer.*

**Endpoints under test:** `GET /stallowners/queue`, `POST /stallowners/queue/advance` (stall owner only, JWT-protected)

**Behaviour:** the queue is a stall's active orders for the current day (`pending` / `preparing` / `ready`), ordered by queue number - the head is the *current* customer. Advancing marks the head order `completed` (in a transaction) and promotes the next order to current. When a next customer exists, the back-end calls the **Brevo transactional email API** (third-party, invoked from the back-end) to email them "you're next", records the send in the `Notification` table, and returns `notified` in the response. A failed email never fails the serve action (recorded as `status: 'failed'`, `notified: false`).

**Evidence:** Postman screenshots in [`screenshots/hayder-zikry/feature5-queue-management/`](./screenshots/hayder-zikry/feature5-queue-management/)

## Feature 6 - View & Follow Up on Stall Complaints (NEA Officer Oversight)

**User Story:** *As a NEA Officer, I would like to view complaints submitted about stalls, so that I could investigate and take appropriate follow-up action.*

**Endpoints under test:** `GET /officers/complaints`, `PUT /officers/complaints/:complaintID/status` (NEA officer only, JWT-protected)

**Behaviour:** unlike the stall-owner complaint view (which is scoped to one stall), the officer view returns complaints across **every** stall, newest first - each row carries the stall, its hawker centre and the customer who raised it. The list accepts three **optional** query filters (`status`, `stallID`, `category`) that can be combined to narrow an investigation; no query string means "show everything". Recording follow-up action moves a complaint through `open → underReview → resolved/closed`; there is **no ownership check** because an officer has authority over all stalls, and `resolvedAt` is stamped when the complaint is resolved/closed and cleared again if it is reopened.

**Evidence:** Postman screenshots in [`screenshots/hayder-zikry/feature6-officer-complaints/`](./screenshots/hayder-zikry/feature6-officer-complaints/)

### How to authenticate

All requests need an officer JWT. First `POST /officers/login` with `{ "email": "mary@email.com", "password": "Mary123!" }`, copy the returned `token`, and set the header `Authorization: Bearer <token>` on every request below. For the wrong-role cases, log in instead as a customer: `POST /customers/login` with `{ "email": "alice@email.com", "password": "Alice123!" }`.

## Feature 8 - Menu Item Image Upload

**User Story:** *As a Stall Owner, I would like to upload a photo for each of my menu items via Cloudinary, so that customers could see what a dish looks like before ordering, making my stall more appealing on the platform.*

**Endpoints under test:** `POST /menuitems`, `PUT /menuitems/:id` (stall owner only, JWT-protected) — extends Feature 2's Create/Update Menu Item endpoints with an optional `image` file field, handled by `uploadMenuItemImage` (Multer + Cloudinary).

**Evidence:** Postman screenshots in [`screenshots/muhammad-bin-riadi/feature8-upload-menu-item-image/`](./screenshots/muhammad-bin-riadi/feature8-upload-menu-item-image/)

> Feature 2 already covers auth (`401`/`403`), ownership (`403`), not-found (`404`), and Joi field validation (`400`) for these two endpoints. Since `uploadMenuItemImage` runs after `verifyJWT` but before the Joi validator, those guards behave identically whether or not an image is attached, so they aren't repeated here — this feature isolates what's actually new: the optional `image` file field.

### Test cases — Create Menu Item with Image (`POST /menuitems`)


| # | Request                      | Expected                                                         | What it proves                                                                                                                                                |
| --- | ------------------------------ | ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 | Create - Success, No Image   | `201` + new item, `imageURL: null`                               | Image field is optional; the existing JSON-only flow from Feature 2 still works unaffected by the new middleware                                              |
| 2 | Create - Success, With Image | `201` + new item, `imageURL` set to a Cloudinary URL             | Valid image upload (jpeg/png/webp) is accepted, stored on Cloudinary, and the URL is persisted                                                                |
| 3 | Create - Invalid File Type   | `400` `{"error":"Only JPEG, PNG, and WEBP images are allowed."}` | Multer's file filter rejects non-image types (e.g.`.pdf`, `.gif`) — uses `error`, not `message`, since it comes from the global handler in `app.js`, not Joi |
| 4 | Create - File Too Large      | `400` `{"error":"File too large"}`                               | Multer enforces the 5MB size limit                                                                                                                            |
| 5 | Create - Wrong Field Name    | `400` `{"error":"Unexpected field"}`                             | Multer rejects a file sent under a field name other than`image` (e.g. `photo`)                                                                                |

### Test cases — Update Menu Item Image (`PUT /menuitems/:id`)


| # | Request                           | Expected                                            | What it proves                                                                    |
| --- | ----------------------------------- | ----------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 6 | Update - Success, No New Image    | `200` + updated item, existing `imageURL` preserved | Omitting the image field on update leaves the previously uploaded image untouched |
| 7 | Update - Success, Replacing Image | `200` + updated item, new `imageURL`                | A new image upload replaces the previously stored one                             |

Seeded stall owner credentials: `diana@email.com` / `Diana123!` (owns Stall 1, `menuItemID` 1–3, used for cases 6 & 7)

> Cases 3–5 (invalid type / too large / wrong field) are only exercised on `POST /menuitems`. `uploadMenuItemImage` is the same middleware instance on both routes, so this is a property of the middleware, not the route — re-testing it on `PUT` would be redundant.
